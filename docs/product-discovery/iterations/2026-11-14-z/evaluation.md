## Базовый способ и набор примеров (№36)

**Базовый способ** решает ту же задачу на тех же данных без LLM: те же 5-6 проверок правилами, а найденное выводится по шаблонам текста («У облигации оферта через 12 дней»). Для поста базовый способ ищет в тексте тикер и числа и сверяет их с данными. Это сильная альтернатива: она получает все данные и правила, отличается только отсутствием понимания текста и объяснения.

**Набор примеров.**

| Параметр | Решение |
|---|---|
| Единица | Сценарий: заявка (бумага, направление, количество, дата), портфель клиента на дату, при наличии пост |
| Объём | 40 сценариев: 10 для настройки, 30 для итоговой проверки |
| Источник | Исторические данные T-Invest API и публичные события: облигации с офертами и амортизацией, выпуски с техническим дефолтом, публичные кейсы манипуляций из сообщений Банка России, обычные сделки без рисков |
| Посты | Реальные публичные посты по кейсам манипуляций и нейтральные посты о тех же бумагах. Синтетические посты помечаются отдельно |
| Эталон | Финансовый проверяющий команды до запуска систем размечает для каждого сценария существенные риски и что из поста не подтверждается данными |
| Утечка | Набор настройки и итоговый не пересекаются по бумагам. Исход сделки после даты сценария не попадает во вход |

**Типы сценариев:** облигация с офертой в ближайшие 30 дней, облигация с амортизацией или плавающим купоном, эмитент с техническим дефолтом, бумага во время разгона по публичному кейсу, отчётность через несколько дней, сделка, которая делает бумагу больше 30% портфеля, продажа до трёх лет владения, обычная сделка без рисков.

## Протокол первого эксперимента (№25)

| Пункт поля 9 | Содержание |
|---|---|
| Гипотеза | Агент с LLM даёт клиенту полный и верный разбор существенных рисков сделки чаще, чем правила с шаблонами на тех же данных |
| Данные | 30 итоговых сценариев из набора выше с эталоном финансового проверяющего |
| Базовый способ | Те же проверки правилами и шаблоны текста, без LLM |
| Метрика | Доля сценариев с корректной карточкой: названы все существенные риски из эталона, у каждого верный источник в данных, нет выдуманных рисков, утверждения поста верно отмечены |
| Порог | Не ниже 80% и не меньше чем на 15 процентных пунктов выше базового способа |

**Порядок.** Настроить инструкции на 10 сценариях, заморозить, прогнать оба способа на 30 итоговых, по 3 прогона LLM для оценки разброса. Карточки оценивает проверяющий, не зная, каким способом они получены.

**Откуда порог.** Предложение для согласования. 80% соответствует порогу из [roadmap Димы](../../roadmap.md) для похожей метрики. Разрыв 15 п.п. нужен, чтобы преимущество не объяснялось разбросом. Уточнить после пилота.

**Интерпретация.** Если порог достигнут, гипотеза подтверждена на наборе и следующий шаг проверка на реальных клиентах. Если разрыв с базовым меньше 15 п.п., LLM не нужна и продукт делается на правилах. Если оба ниже 80%, пересматриваем проверки или набор.

## Стоп-факторы (№26)

| Риск | Что может не сработать | Почему критично | Ранняя проверка |
|---|---|---|---|
| Востребованность | Клиенты игнорируют карточку или отключают проверку | Продукт не меняет решения | Показать прототип карточки 3-5 инвесторам на их недавних сделках |
| Регулирование | Предупреждение читается как индивидуальная рекомендация | Для Т-Банка это регуляторный риск, внедрения не будет | Формулировки только о фактах и последствиях, сверить с маркировкой выводов агентов Т-Инвестиций |
| Качество AI | LLM пропускает существенный риск или выдумывает несуществующий | Ложное спокойствие хуже отсутствия проверки | Пилот на 10 сценариях, валидатор утверждений по данным |
| Данные | В MCP или в песочнице нет событий облигаций, инсайдеров или календаря отчётности | Ключевые проверки невозможны | `tools/list` MCP и пробные вызовы токеном только на чтение до разработки |
| Необходимость AI | Правила с шаблонами дают тот же результат | LLM только удорожает | Первый эксперимент, разрыв с базовым способом |

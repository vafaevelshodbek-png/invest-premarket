## Продукт и изменение для пользователя (№4)

| Пункт поля 2 | Описание |
|---|---|
| Область | Подготовка и исполнение сделок частного инвестора у брокера: шаг между решением купить или продать и подтверждением заявки |
| Пользователь | Частный инвестор Т-Инвестиций, который торгует сам или через подключённого ИИ-агента по MCP |
| Задача | Перед подтверждением заявки понять, нет ли у сделки скрытых последствий, которые он не учёл: оферта или амортизация облигации, риск дефолта эмитента, признаки разгона бумаги, отчётность через два дня, перекос портфеля, налог при продаже |
| Текущий способ | Клиент сам открывает карточку бумаги, календарь событий, график, новости и Пульс. Каждую проверку надо вспомнить и сделать вручную. Агент по MCP выставит заявку по команде, но не обязан проверять её последствия |
| Формат | Агент встраивается в шаг подтверждения: в чате с ИИ-агентом, в Telegram-боте или как отдельный экран «проверить перед покупкой». Выдаёт короткую карточку: что найдено, почему это важно, источник, что проверить. Клиент подтверждает, меняет или отменяет заявку сам |
| Ожидаемое изменение | Клиент видит существенные последствия до сделки, а не после. Ожидаем меньше сделок, о которых потом жалеют, и меньше обращений в поддержку по ним. Эффект не измерялся |

**Чего продукт не делает.** Не советует купить или продать, не выбирает бумагу, не выставляет заявку без подтверждения, не прогнозирует цену.

## Паспорт сценария (№21)

| Элемент | Описание |
|---|---|
| Триггер | Клиент сформулировал заявку (сам или через агента) и собирается её подтвердить. Дополнительно может приложить текст поста, по которому решил купить |
| Пользователь | Частный инвестор с токеном Т-Инвестиций только на чтение для проверки и отдельным правом торговли для исполнения |
| Входы | Параметры заявки: бумага, направление, количество, цена. Портфель и операции клиента. Данные бумаги из API. Необязательно: текст поста |
| Результат | Карточка проверки: 0-5 найденных рисков, у каждого объяснение, источник в данных и что сделать. Если рисков нет, это сказано прямо. Если данных не хватило, перечислено, что не проверено |
| Получатель | Сам клиент |
| Следующее действие | Клиент подтверждает заявку, меняет её или отменяет. Подтверждённая заявка уходит через MCP |
| Границы первой версии | Облигации и акции Мосбиржи, рублёвые инструменты, обычные лимитные и рыночные заявки. Вне первой версии: фьючерсы, опционы, маржинальная торговля, валюта |
| Вне системы | Выбор бумаги, совет купить или продать, прогноз цены, исполнение без подтверждения |

## Шаги сценария и отказы (№34)

| № | Шаг | Исполнитель | Выход |
|---|---|---|---|
| 1 | Клиент формулирует заявку и при желании прикладывает пост | Клиент | Черновик заявки |
| 2 | Определить инструмент и параметры, уточнить при неоднозначности | Код, при свободном тексте LLM с уточняющим вопросом | Однозначный инструмент и параметры |
| 3 | Собрать данные: бумага, события облигации, свечи и объёмы, сделки инсайдеров, календарь отчётности, портфель, операции | Код через MCP или API, только чтение | Снимок данных с временем получения |
| 4 | Прогнать проверки правилами: событие в ближайшие 30 дней, флаги облигации, всплеск объёма и цены относительно истории, доля бумаги в портфеле после сделки, срок владения при продаже | Код | Список сработавших проверок с числами |
| 5 | Если приложен пост, выделить утверждения и сверить их с данными | LLM, сверку чисел делает код | Утверждения с отметкой «подтверждено», «противоречит данным», «нельзя проверить» |
| 6 | Отобрать существенное, объяснить простыми словами, связать с параметрами заявки | LLM по проверенным фактам | Проект карточки |
| 7 | Проверить, что каждое утверждение карточки опирается на число или поле из снимка | Код | Карточка или отброшенные утверждения |
| 8 | Клиент решает. Если подтверждает, заявка уходит через MCP | Клиент, MCP | Заявка или отказ |

| Отказ | Поведение |
|---|---|
| Инструмент не определён однозначно | Уточняющий вопрос, проверка не запускается до ответа |
| Метод API недоступен или вернул ошибку | Проверка помечается как невыполненная, карточка прямо говорит, что не проверено |
| LLM сформулировала утверждение без опоры на данные | Утверждение удаляется валидатором и попадает в журнал |
| Данных об отчётности или событиях нет | Сказано «событий не найдено в данных», а не «событий нет» |
| Модель недоступна | Клиент получает результат правил без текста объяснения |
| Клиент спешит | Можно подтвердить сразу, проверка не блокирует сделку |

## Востребованность и встраивание (№37)

**Пользователь** является частным инвестором. **Покупатель** по гипотезе Т-Инвестиции как функция приложения или MCP-агента. **Владелец данных** Т-Инвестиции и сам клиент.

| Риск | Почему критичен | Основание или гипотеза | Ранняя проверка |
|---|---|---|---|
| Клиенты игнорируют предупреждения | Продукт не меняет поведение | Гипотеза, известный эффект «усталости от предупреждений» | Показать прототип карточки 3-5 инвесторам, спросить, что бы они сделали |
| Предупреждение воспринимается как рекомендация | Регуляторный риск для брокера | Индивидуальные рекомендации требуют аккредитации программы, [Financial One](https://fomag.ru/news/roboedvayzery-i-avtokonsultanty-poluchili-akkreditatsiyu-ot-naufor) | Формулировки только о фактах и последствиях, без «купите» и «продайте», маркировка как у Т-Инвестиций |
| Проверка замедляет сделку | Активные трейдеры отключат функцию | Гипотеза | Проверка за несколько секунд, кнопка «подтвердить сразу» |
| Брокер сам встроит такую проверку | Отличие исчезнет | Т-Банк обещает внедрять лучшие решения хакатона, это скорее плюс | Позиционировать как функцию для Т-Инвестиций, а не конкурента |
| Ложные тревоги | Клиент перестаёт доверять | Гипотеза | Порог существенности в правилах, проверка на наборе примеров |

Гипотезы спроса и готовности применять продукт не проверены, наблюдений пользователей у команды пока нет.
